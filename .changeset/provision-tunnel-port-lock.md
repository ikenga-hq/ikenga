`provision.sh tunnels`: a tunnel's local end (`127.0.0.1:<port>`) was reachable by every account on the box, and while the tunnel was down any account could bind the port and receive the backup job's connection, login included. Two fixes. (1) **Port lock**: for each tunnel port an nftables table of its own, `inet ikenga_tunnels` (loaded at boot by `ikenga-tunnel-lock.service`; ufw cannot match on the user and `ufw --force reset` never touches it), rejects `tcp dport <port>` on `127.0.0.1` and `::1` from every uid except root and the new profile key `TUNNEL_ALLOW_USERS` (default: the backup user when `BACKUPS_ENABLED=1`, else root only). Tunnels `Require` the lock through a drop-in, so it fails closed; a rerun reports `no changes`, repairs drift (deleted table or rule, extra accept rule), and a tunnel removed from the profile loses its rules. (2) **`require_auth`**: nft cannot stop a `bind()` (and `ip_local_reserved_ports` does not stop an explicit one), so the backup job now pins authentication: `run-backup.sh` accepts `require_auth` in the connection string and a per-database `"require_auth"` in `BACKUP_CONFIG` (`PGREQUIREAUTH` in the `pg_dump` environment; `false` opts out), defaulting to `scram-sha-256` for any database whose connection string points at loopback on one of the box's tunnel ports. A fake server then gets no password and cannot feed a forged dump; the run reports the new status kind `auth-refused`. New container suite `test-portlock-container.sh` (real systemd and nf_tables, a real restart, squatting against a fake Postgres through the real job).
