`chi_run` takes an optional `toolPolicy` that limits what a Claude Code run can do, so a caller serving a person with a restricted toolset (the Mattermost bridge) can enforce it in the daemon instead of in a prompt. The policy is `{ tools, allowedTools, disallowedTools, mode, strictMcp, settingSources }`: the daemon builds the claude argv with `--tools`, `--allowedTools` and `--disallowedTools` (one argv element per rule), `--strict-mcp-config` with no MCP config, `--setting-sources` as given and `--disable-slash-commands`, and runs it in `dontAsk` mode, which denies any tool that is not allowed immediately, with no prompt and no `awaiting_auth` parking. If the engine asks for a decision anyway, the run is killed and failed rather than left waiting. The policy is stored with the run (migration 0073) and re-applied on `chi_resume`; a policy run whose stored policy is missing or unreadable refuses to resume rather than run unrestricted. An unknown or malformed policy field, an explicit `null`, or a policy on an engine other than claude-code fails the call and creates no run. A `persistent` policy run stays in-process (the detached chi-runner builds its own argv and cannot apply a policy), says so in the result's `error`, and does not survive a daemon restart. Allow rules do not confine reads: read-only Bash commands and Read still run, so the run's cwd stays the read boundary. `/api/health` now returns `capabilities: ["chi.toolPolicy"]`, which a client must check before starting a policy run; a daemon without it cannot apply one. Runs without `toolPolicy` are unchanged.
