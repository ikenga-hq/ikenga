## Execution model

- **Orchestrator** owns wave sequencing, gate sign-off, branch/PR ownership, merge order, conflict resolution, `05-tracking.md` writes, the Phase 4 close report.
- **Subagents** own exactly one WP each, receive the `### WP-NN` brief below verbatim, work on the named branch in the named repo, self-check against their Definition of Done, and report `done / blocked / needs-decision` with `designs_implemented: []` (Phase 4 builds no designed surface).
- **Isolation axis: git repo + disjoint dirs.** Wave 9a runs three WPs in three different repos (`contract/`, `shell/`, `iyke-cli/` + `ikenga-pkgs/packages/mcp/mcp-iyke/`). Use **worktrees** for parallel WPs in the same repo (only wave 9c/9d touch `shell/` again, sequentially); plain branches suffice across repos.
- **Workspace link**: after WP-27 publishes, run `pnpm install` at the ikenga workspace root so `shell/` resolves `@ikenga/contract@0.19` via `workspace:*` before WP-28's TS parity test lands.
- **Integration branch**: `feat/phase-4-manifest-v5` in `ikenga` (shell) for WP-28, WP-31, WP-31a. WP-27 (contract), WP-21b (iyke-cli, mcp-iyke), WP-29 (ikenga-pkgs), WP-30 (ikenga-registry) each ship on their own repo's `main` via PR. **Shell CI runs on every PR, including into the integration branch — `gh pr checks` must be green before any merge** (Round 19 lesson: never merge over red).
- **Machine claim**: check the shared-machine quiet window before heavy runs (`cargo build --release`, full shell suite).

## Mock contract (so cross-boundary agents don't serialize)

### 1. v5 types before `@ikenga/contract@0.19` publishes (lets WP-28 start beside WP-27)
WP-28 codes the Rust side directly from `drafts/g-manifest-v5.md` §2 (the frozen text, not the TS file). Owner of the fixture set: WP-28. If WP-27 finds §2 unimplementable as written, that is a **new Round**, and the orchestrator pauses WP-28.

### 2. Bridge routes for WP-21b — SUPERSEDED (Round 26, G-31)
The assumption was wrong: `ngwa_snapshot` was a Tauri command only. The routes `GET /iyke/ngwa/snapshot` and `GET /iyke/explorer/sections` (`BRIDGE_API` 3) ship in #240 under WP-28; until it merges every `iyke ngwa *` subcommand returns an actionable missing-route error.

### 3. Registry catalog for WP-29 → WP-30
Registry entries (`ikenga-registry/pkgs/<short>.json`) carry the **full manifest** per version, so the Store already sees `ui.views[]` once WP-29 publishes — WP-30 needs no schema change for that. Signing is done by `ikenga-pkgs` CI (`REGISTRY_SIGNING_PRIVATE_KEY`, minisign on the runner); no agent ever handles keys (answers open question #2).
